## Observations

After 62 verification runs of "root HTTP 404 behind green Pages builds", the
mechanism is now fully established with direct evidence:

1. **Pages configuration**: `gh api .../pages` →
   `{"source": {"branch": "main", "path": "/"}, "build_type": "legacy"}` —
   GitHub Pages publishes the **`main` branch root directory**.
2. **Where the site actually builds**: `npm run build` runs
   `scripts/build-pages.js` and emits the complete site to **`dist/`**
   (verified this run: `dist/index.html` 23,955 bytes, `dist/styles.css`
   28,980 bytes, 2 school pages under `dist/provinsi/.../`, `schools.json`,
   `schools.csv`, 404.html, robots.txt).
3. **`dist/` is never published**: `dist/` is in `.gitignore` (lines 10,
   236), is NOT tracked in git (`git ls-files dist/` → empty), and **no
   workflow contains any Pages deployment step** — zero occurrences of
   `actions/deploy-pages`, `actions/upload-pages`, `actions/configure-pages`,
   or `gh-pages` in `.github/workflows/` (grep across all 6 workflows +
   on-pull/on-push).
4. **What the live site actually serves**: only files committed at `main`
   root that Pages serves statically — `.nojekyll`, `robots.txt` (200), and
   the **empty placeholder** `sitemap-index.xml` (200, contains only the
   comment `<!-- Sitemaps will be generated by scripts/sitemap.js -->`).
   Every real page 404s.

### Pages build streak is real but meaningless for users

`gh api pages/builds` shows 6 consecutive `built` at HEAD (fb2d5ab → 9d48a06),
status `built` on the latest build. But "built" only means GitHub successfully
deployed the **repo root** — it deploys the source branch content, not the
`dist/` output. The green Pages status and the 404s are fully consistent.

## Evidence

- `gh api repos/sulhimaskom/sekolah-pseo/pages` → source branch `main`, path `/`, `build_type: legacy`, `status: built`.
- `gh api repos/sulhimaskom/sekolah-pseo/pages/builds?per_page=12` → 6× `built` at HEAD commits, 1 `errored` (241fd21, 2026-08-06 13:56).
- `npm run build` → exit 0, dist/ fully populated (verified `ls dist/`).
- `git ls-files dist/` → empty (not tracked); `.gitignore:10,236` → `dist/`.
- `grep -rn "deploy-pages|upload-pages|configure-pages|gh-pages" .github/` → **no matches**.
- Live `curl` probes → root/index/styles/schools.csv 404 (3× re-probe), robots/sitemap-index 200.
- `robots.txt` (committed) → `Sitemap: https://example.com/sitemap-index.xml` — placeholder SITE_URL (F006), further proof the committed root is a template, not a deployed site.

## Impact / Risk

The product has **no reachable website** despite green build + green Pages +
green CI. Every downstream artifact (sitemap, SEO, school pages, CSV
download) is unreachable by users. The `schools.csv` regression (200→404 this
run) shows the root-served static set can only shrink, never improve, while
the real site stays in gitignored `dist/`. F025 is the highest-impact _user
facing_ finding in the ledger.

## Suggested resolution (not implemented — read-only audit)

1. **Minimal**: add a Pages deploy stage to `on-pull.yml` (or a dedicated
   `deploy.yml`): build → `actions/configure-pages` + `actions/upload-pages`
   (artifact: `dist/`) → `actions/deploy-pages`. Requires Pages source set to
   "GitHub Actions" (config change: `gh api -X POST .../pages` source
   `{"branch":"main","path":"/"}` → actions-based) — **requires
   `workflows: write` (F050) + Pages write permission; org grant needed**.
2. Alternative (no workflow change): switch Pages source to a `gh-pages`
   branch populated by committing `dist/` — heavier, pollutes history,
   not recommended.
3. Fix `robots.txt` SITE_URL (F006) in the same change so the committed root
   template stops advertising `https://example.com`.
